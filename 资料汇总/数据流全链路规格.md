# 龙舟 VR 力反馈系统 —— 数据流全链路规格

2026-10-31 按最终设备形态补充：桨的实际运动由人的划桨动作和机构可达范围决定，软件消费传感器姿态计算水动力，再向电机和平台输出反馈。电脑中的脚本意图及握持动力学用于无硬件测试，不作为人体手感模型的验收。显式 `-cad-tendon-rig` 模拟入口在独立控制器生成编码器之前加入理想机械限位；其保守包络由当前显示的船体及桨尺寸得到，包含装饰几何，具体实机行程/角度仍未测量。真实传感器输入不按脚本轨迹回拉。

> 原设计版本：2026-10-20；接口与范围说明核对：2026-10-31。
> 约定：每个数据都写清 **谁产生 → 什么格式 → 走什么通道 → 谁消费 → 谁解算**。
> 下文原有 ✅ 和数值是历史软件检查记录，不是当前全链路或实机通过证明。当前验收见根目录《软件全链路闭环验收.md》及具体运行目录；当前修复进度见 `tmp/closed_loop_20261025/IMPLEMENTATION_STATUS.md`。
> ❓ 表示实物参数或协议尚未确认；本期允许明确标注的简化模型与固定数据承担对外功能，不要求模拟传感器内部零件。

## 0. 全链路总览（一行版）

```
人划桨
  → [传感层] 编码器/PCB 采桨位姿
  → [上行通道] 位姿数据包
  → [中游·上位机] 水动力解算 + 船体六自由度解算
  → 分四路输出：
      ① 视觉端：VR 画面渲染（船/水/岸/桨/浪花）
      ② 力反馈端：水阻力 → 各电机张力指令 → 下位机 → 绕线轮 → 绳 → 手
      ③ 平台端：船姿态 → 六缸长度指令 → 六轴平台 → 身体
      ④ 声音端：实际入/出水、相对水速、木质接触和受载摇动 → 音源 → 听者
  → 人的感受回流成下一桨（闭环）
```

## 1. 数据源：划桨动作（唯一源头）

| 项 | 内容 |
|---|---|
| 物理量 | 桨的位姿随时间的函数：位置 P(t)=(x,y,z)，姿态 R(t)（欧拉角或四元数） |
| 产生者 | 人 |
| 采样者 | 桨上的编码器 + 自研 PCB |
| 状态 | ❓ 采样什么、怎么采，待问（见 §7 清单） |

划桨是推进动作的输入源；波浪和水流是独立环境输入。不划桨时仍有船体惯性、波浪起伏、随流漂移和相应视觉/平台响应，不能把全链静止作为验收条件。

## 2. 传感层：编码器 + PCB —— 本地处理还是上传原始值？

这是架构级岔路，两种做法都存在，**必须问**，不能猜：

| 方案 | 做法 | 后果 |
|---|---|---|
| A. 本地预处理 | PCB 上的 MCU 把编码器脉冲解算成"桨位姿"，打包发给上位机 | 上位机收到即用；PCB 程序是黑盒，格式由硬件组定义 |
| B. 原始值上传 | PCB 只转发脉冲计数/ADC 原始值，上位机自己解算 | 上位机要拿到编码器线数、传动比、安装几何才能换算 |

**待问**：PCB 固件做的是 A 还是 B？输出接口是串口/CAN/USB/以太网？输出帧格式与频率？

**当前软件接口（按实现核对，均不等于实物固件协议）**：

| 路径 | 谁产生 → 数据/通道 → 谁消费 | 对外作用与边界 |
|---|---|---|
| 默认动态闭环的传感上行 | 独立 `closed_loop_controller.py` 的实际桨状态 → 52 字节 DBEP（六路编码计数、握持模型合力大小、采样时间、序号、CRC32），嵌入带会话/序号/CRC 的 DBCL UDP 反馈 → `UdpClosedLoopClient` / `PaddleEncoderPipeline` | 位置 10000 counts/m、角度 100 counts/deg；解码结果进入实际桨显示与水动力。直接量化是可替换的传感器功能模型，不能冒充实测安装拓扑 |
| 默认动态闭环的执行下行 | 水动力/三绳分配、船体/平台逆解 → DBCL UDP 命令（各绳目标张力、来源速度/耗散、六缸目标长度、有效标志等）→ 独立控制器 | 控制器每 5 ms 按当前实际运动削减已过时的水阻目标，再积分原电机响应；有效目标、实际滞后张力及实际缸长/FK 位姿分别回传。执行力、力矩和平台惯性影响下一次桨测量 |

**当前 DBCL 运动与阻力字段**（JSON 负载；源码契约为 `ClosedLoopContracts.cs`，不代表真实固件已支持）：

|---|---|
| 命令 `desiredGripPosition/Rotation/Velocity/AngularVelocity` | 船体/平台局部坐标；m、四元数 xyzw、m/s、rad/s。目标导数使用不同 `controllerTimeSeconds` 的间隔；角阻尼作用于目标与实际角速度之差 |
| 命令 `sourceFeedbackSequence/sourceSampleTick` | 指向控制器实际发出的一次观测；控制器核对历史身份，执行期限也受该来源观测的 100 ms 墙钟时效约束 |

`controllerTimeSeconds = plantSampleTick × 0.005` 只表示实际已积分的时间；控制器另报墙钟与丢弃步数。采样导数不能使用 Unity 连续补帧时的调用间隔，100 ms 失效保护也不能改用较慢的积分时钟。主机和随包控制器需配套更新；当前主机拒绝缺少新执行反馈字段的回包。验收文件的 `schemaVersion=5` 是证据结构版本，新增前四个实际物理步的显示碰撞体观测；不是新的实机协议号。

## 3. 中游（上位机）：两个核心解算

上位机收到桨位姿后，必须依次算两样东西。这两步**已在 Unity 仿真侧实现并验证 ✅**。

### 3.1 水动力解算：桨位姿 → 水阻力

- **输入**：桨位姿 P(t)、R(t)（来自 §2）；水面高度场 η(x,z,t)（来自 §3.3）
- **解算**：由桨杆几何推出**桨叶中心**位置与速度 v_blade；判断桨叶是否入水；入水则：

```
F_water = −½ · ρ · Cd · A · |v_rel| · v_rel
  ρ  = 1000 kg/m³（水密度）
  Cd ≈ 1.1（桨叶阻力系数）
  A  = 桨叶浸水面积（随入水深度变化）
  v_rel = 桨叶相对水的速度
```

- **输出**：水对桨的力 **F_water(t)**（N）及分布力矩。上式的负号已经表示阻力反对桨的相对水速；当前船体等效推进保留此力的水平同向分量，按 `propulsionScale` 缩放，并对竖向施加 `propulsionVerticalDamp`。不能再额外取负号，否则会把船推向相反方向。握把反馈另经限幅和平滑，不能与未限幅的原始水动力混为一谈。
- **反馈平滑**：力与力矩保持当前原始方向，以同一个非负增益缩放；仅平滑幅值增长，减小立即跟随，避免换向后旧方向反而驱动桨。相对水流耗散功率随同一个增益送入 DBCL；干桨/零输出不保留旧耗散。最终握把处仍整体限幅，原始船体受力不经这层反馈处理。
- **实测（仿真）**：峰值 ≈196N，入水段均值 ≈91N，脉动节奏与划桨一致 ✅
- **当前负责方**：Unity 上位机计算分布水动力；独立控制器只进行下文声明的局部目标削减与执行器/握持积分。实物 MCU 的具体计算分工未确认。

### 3.2 船体六自由度解算：推进力 + 波浪力 → 船的姿态

- **输入**：F_propulsion（来自 §3.1）；波浪力（§3.3）；船体参数（质量≈150kg 等效、湿面积≈2.1m²、水线面惯性）
- **解算**：当前 Unity 刚体固定步长为 0.01 s（标称 100 Hz），独立执行器/握持模型为 0.005 s（标称 200 Hz）；均不等于 Windows 墙钟准时调度保证。
- **输出**（每个仿真步一份）：

| 数据 | 符号 | 单位 | 用途 |
|---|---|---|---|
| 位置 | boatPos = (x, y, z) | m | 视觉端相机/场景 |
| 姿态 | roll, pitch, yaw | 度 | 视觉端 + 平台端 |
| 速度 | v = (vx, vy, vz) | m/s | 尾迹、浪花强度 |
| 升沉 | heave = y | m | 平台端 |
| 加速度 | a_local | m/s² | 平台前馈（可选） |

- **实测（仿真）**：吃水 17.7cm（理论 18.0），巡航 0.63m/s，横摇 ≈7° ✅

### 3.3 波浪场：独立的时间驱动模型

- **输入**：采样位置 (x,z)、仿真时间 t 和当前场景的波谱配置；波浪持续演化不依赖是否划桨。
- **输出**：水面高度场 η(x,z,t)（解析波叠加，不需要外部数据）
- **消费方**：§3.1（判桨叶入水）、§3.2（波浪力）、§5 视觉端（水面起伏）
- 状态：✅ 已实现

## 4. 力分配解算：水阻力 → 每台电机的张力（核心环节）

### 4.1 它在哪算、上一步是谁

- **上一步**：§3.1 将原始水动力换算到握把参考点，经过既有反馈限幅和平滑，形成 `ForceFeedbackRequest` 中的目标力 `forceWorldN` 和握把力矩 `torqueAtGripWorldNm`。分配器消费这份请求，不能把未限幅的原始水动力直接当成电机目标。
- **当前在哪算**：Unity 上位机按同一输入观测的绳路几何求解完整有界分配。独立控制器消费目标并执行局部水阻削减、张力响应和实际力矩计算；这里不据此推定真实 MCU 的算力或固件分工。

### 4.2 怎么算

绳子只能拉不能推。设第 i 根绳的桨上拴点为 A_i，离桨最近的有效导向点为 G_i，握把参考点为 P_grip；三者先换到同一坐标系。桨上的拉力沿自由绳段指向 G_i，因此单位方向 u_i = (G_i − A_i) / |G_i − A_i|，力臂 r_i = A_i − P_grip。多级滑轮形成的整条折线路径用于核对走绳和长度，不能把整条折线当成一个受力方向。

```
求 t = (t1, t2, …, tn)，n = 绳的根数：
  使  Σ ti·u_i            ≈ F_request   （请求力的 3 个分量）
  且  Σ ti·(r_i × u_i)    ≈ τ_request   （握把处请求力矩的 3 个分量）
  约束 minTension_i ≤ ti ≤ maxTension_i（有效执行保留原预紧，失效目标归零）
解法：有界最小二乘；当前三绳枚举活动集并检查 KKT，多绳保留迭代求解路径
```

当前实现用每根绳的 `anchorLocal` 作为等效导向点、`attachLocal` 作为桨上拴点；分配器按同一个特征长度归一化目标力矩和各绳力矩，再联合求解。`cableLengthsMm` 表示这两个点之间的自由绳段距离，单位 mm。Unity 与独立控制器均按此单段几何计算，它不是整条多滑轮绳路的总长度，也不是卷轮累计放绳量；当前模型没有据此验证滑轮摩擦或真实传动。依据：[CableDriveTwin](../DragonBoatVR/Assets/Scripts/CableDriveTwin.cs)、[TendonRigSolver](../DragonBoatVR/Assets/Scripts/TendonRigSolver.cs)、[独立控制器](../DragonBoatVR/Assets/StreamingAssets/closed_loop_controller.py)。

### 4.3 算之前必须先拿到的参数（缺一个就算不准）

| 参数 | 用途 | 状态 |
|---|---|---|
| 绳的根数 n、与电机的对应关系 | 定未知数个数与通道身份 | 本项目已确定三绳；软件映射已配置，真实电机通道仍待核对 |
| 每个拴点在桨上的位置 | 力臂 r_i | 软件有配置；用户已确认的安装事实保持，其余几何仍需实测 |
| 末级导向点及其余滑轮坐标 | 末级点确定桨上力方向；其余点参与完整走绳和总长计算 | 当前使用等效单段几何，不能将其当成完整实物绳路标定 |
| 有效卷绕半径、减速比 | 电机力矩 ↔ 绳张力换算 | ❓；CAD 卷轮外径不等于有效卷绕半径 |
| 电机额定/峰值扭矩 | 张力上限约束 | ❓（铭牌在，拍照即可） |
| 电机铭牌型号 | 查扭矩-电流曲线 | ❓ |

### 4.4 输出（上位机 → 下位机的指令）

- **内容**：每台电机的目标张力（N）或目标力矩（N·m）——具体用哪种 ❓待问
- **格式与协议**：❓ 待问（串口？CAN？帧结构？频率？）
- **当前默认仿真执行通路**：每个 Unity 固定步生成 DBCL 命令，独立控制器消费各绳目标张力并回报实际张力、力/力矩与后续测量。48 字节 BoatState 的阻力/姿态回显是诊断通路，不是各电机指令。标称固定步不代表 Windows 墙钟调度有硬实时保证；真机协议仍以硬件组答复为准。

有效水阻命令在控制器每个 5 ms 步内，根据来源耗散 `D > 0`、来源完整握把力/力矩 `W` 和实际握把线/角速度相对来源的变化 `ΔV`，计算 `g = clamp(1 - W·ΔV / D, 0, 1)^2`；每绳有效目标为 `minTension + (target - minTension) × g`。新出现或增大的水阻需等待新主机样本；不放大旧目标。然后按原 `motorTauSeconds=0.035`、`motorSlewNPerSecond=2000` 及张力上界积分实际张力，过期时目标为零而实际尾力继续如实回报。

上述公式在共线均匀水流下对应二次阻力比例，多维波浪/转动时是局部近似。`D` 包含相对水流的分布功，所以允许流水对桨做正的世界空间功；这不是滞后电机与受限三绳整体被动性或实机保真的证明。数值分配通过也不能消除三根只拉不推的绳在六维力域中的方向缺口。

### 5.1 同步声音的输入与实际输出

完成的物理帧 → `WaterInteractionVisuals` 的运动观察 → `RiverAudioController` / `RiverAudioMotion` → 场景中的七路音源 → `AudioListener` 实际混音。桨跨越水面触发入水/滴水音，湿区相对水速控制持续划水声，船身水平相对水速控制船身水声；桨与模型船舷的接近/触碰及实际船体碰撞触发木音，受载转动与摇动触发低音量吱呀。连续静止接触不重复敲击；停止、重置和过期观察清理相应运动声，正常滑行仍可产生船身水声。

水录音来自 Unity BoatAttack，敲击录音来自 Kenney CC0，吱呀使用 Department64 / AntumDeluge 的 CC0 木材实录；音源跟随作用位置，旧吱呀合成函数已移除。船舷接触轮廓、强度与音色参数是明确的未实测近似。动态验收记录同帧物理来源、各层输出 RMS，并捕获真实监听器 PCM，核对时长、非静音、削波和哈希；这验证声音已到达输出，不代替主观试听或实船声学测量。

## 6. 平台端（六轴）：是下位机，协议必须搞清楚

- **是不是下位机**：**是**。它自己不算船的姿态，只能等上位机给指令。
- **数据链**：§3.2 输出的船姿态（roll, pitch, yaw, heave 等）→ **逆解算**成 6 根电动缸的目标长度：
  `L_i = |T + R·p_i − B_i|`（T=平台位移，R=旋转矩阵，p_i=动平台铰点，B_i=静平台铰点）
- **逆解在哪做，两种做法 ❓待问**：
  - 上位机算好 6 个缸长直接发（平台侧只执行）；
  - 上位机只发姿态角，平台控制器自己逆解（商用平台多是这样）。
- **协议 ❓待问**：什么接口（串口/以太网）、什么帧格式、频率、单位（mm？脉冲？）、有没有状态回报。
- **当前仿真路径**：完成的船体状态 → Unity 平台映射/逆解 → DBCL 六缸目标长度 → 独立控制器的原响应/速度/行程限制 → 实际缸长正运动学 → 实际平台显示、反馈和握持惯性。实际回包拥有平台显示；失效保持实际缸长。平台配对几何仍是未实测假设，旧 0.20°/586～899 mm 数字不作为当前全范围验收标准。
